## 1. 版本摘要

0.9.0 补齐的是**六转（仙窍）之后的玩法**：元气曲线在六转封顶（0.8.0 已封），此后由**仙元**接管续航。仙元刻意**不是副资源**，而是一张停在蛊手牌里的**货币牌**——六转起每场战斗按转数发放一张（青提 / 红枣 / 白荔 / 黄杏，面额 2 / 4 / 8 / 16），六转及以上的蛊牌每次催动在照付元气之外**额外**扣 1 / 2 / 4 / 8 个催动单位；玩家也可以主动打出这张牌，花 1 个单位把元气补满。余额写在卡牌自身的 `SavedAttachedState` 上，随战斗快照与联机同步恢复。

第二条线是**仙蛊唯一**：六转及以上的蛊牌视为「仙蛊」，同名仙蛊整局唯一。仲裁分两处——升转（升炼 / 合练）时先裁，入永久牌组时再裁；落败者被拒绝入牌或降回五转，各联机端并发处理也能收敛到同一胜者。

第三条线是**强化槽的架构替换**：0.8.0 用自研复合载体 `CompanionEnhancementSlot` 占住原版唯一的主附魔字段来模拟双槽，本版改为依赖前置 **MultiEnchantmentMod** 的**旁路额外附魔槽**——原版附魔照旧占主槽、强化进额外槽，两者天然共存，载体与它的 9 个补丁点（约 1400 行）整体删除。在此之上落地了**首批父蛊→子卡强化**（月光蛊 → 月刃强化、玉皮蛊 → 玉皮甲强化）与「每场战斗 N 次」的生命周期。

## 4. 核心玩法系统

### 4.1 仙元：为什么必须是「货币牌」

仙元被刻意设计成**一张卡**而不是 RitsuLib 的副资源，理由有两条：

1. **展示位天然存在**：蛊手牌是一个独立的额外手牌堆，把货币牌停在那里既不占原生手牌，也不需要新 UI；副资源则需要额外做一套数值 HUD。
2. **余额随战斗快照走**：余额写在卡牌自身的 `SavedAttachedState<CardModel,int>` 上（key `GuZhenRenRubild.immortal_essence_units`），随战斗存档与联机同步一起恢复，**不需要任何自研存档字段**；而牌是"每场战斗新生成一张"，所以余额随新牌自然回满。

`ImmortalEssenceSystem` 用 `-1` 表示"从未扣减过"，这样刚生成的牌不需要任何初始化写入；读取时 `-1` 视作满额。

### 4.2 仙元数值与流程

| 项 | 值 | 出处 |
| --- | --- | --- |
| 发放转数 | 六转起（`ApertureProgression.ImmortalRank = 6`） | `ApertureProgression.cs` |
| 档位映射 | 六/七/八/九转 → 青提/红枣/白荔/黄杏（超过九转仍取黄杏） | `ImmortalEssenceSystem.GetEssenceCardForRank` |
| 面额（催动单位） | 2 / 4 / 8 / 16 | 四张牌各自的 `ActivationUnits` |
| 催动附加消耗 | 六/七/八/九转 = 1 / 2 / 4 / 8（`1 << (rank−6)`，封顶 2³） | `ImmortalEssenceSystem.GetActivationCost` |
| 发放时机 | `BeforeHandDraw`（先发杀招推演，再发仙元），同一运行层数只发一次 | `GuZhenRenRubildRelic.BeforeHandDraw` |
| 主动打出 | 花 1 个单位，把元气补满到当前上限（`SecondaryResourceCmd.Set`） | `ImmortalEssenceSystem.PlayEssenceAsync` |
| 扣减顺序 | 余额升序 → `Id.Entry`（先花小面额，避免把大面额牌打散） | `ImmortalEssenceSystem.TrySpend` |
| 耗尽后 | 牌留在原地、不可打出也不再被消耗，直到战斗结束 | `AbstractXianYuanCard.IsPlayable` |

- 可打出判定**刻意不读 `Card.Pile`**：RitsuLib 会在 `CardModel.CanPlay` 期间临时改写牌堆取值（见 0.8.0 的 `ritsulib-cardmodel-pile` 结论），按牌堆判定会直接判死。
- 仙元牌 `CanBeGeneratedInCombat = false`、`MaxUpgradeLevel = 0`，卡图按类名解析 `images/cards/{类名}.png`。
- `CanPayActivation` 只读状态、无副作用，供 `GuCardRuntime.CanActivate` 调用；真正扣费发生在 `BeforeCardPlayed`。

### 4.3 仙蛊唯一

| 项 | 规则 |
| --- | --- |
| 判定 | `GuXianGuRules.IsXianGu(card)`：`AbstractGuCard` 且 `GuRank >= 6` |
| 范围 | **整个 run 的全部玩家永久牌组**（不只当前玩家） |
| 仲裁入口 ①（升转） | `AbstractGuCard.TryIncreaseGuRank` → `GuXianGuRules.TryCommitGuRankIncrease`：整局已有同名仙蛊则不升转 |
| 仲裁入口 ②（入牌） | `Hook.ShouldAddToDeck` 后缀（`XianGuUniquenessPatch`，`Priority.Last`）→ `TryAuthorizePermanentDeckEntry`：冲突时拒绝入牌，或把落败的既有同名仙蛊**降回五转** |
| 优先级 | 首次成仙楼层 → 玩家槽位 → 牌组位置 → 玩家 NetId（`SaveAttachedState` 记录「首次成仙楼层 + 1」） |
| 未登记项 | 旧存档或外部工具产生的仙蛊没有登记，取 `int.MinValue`，视为最早产生，绝不会被新仙蛊顶替 |
| 奖励侧封顶 | `GuRankRewardPatch` 赋阶时若已有同名仙蛊，把采样上限压到五转（**只改采样区间，不额外消耗随机数**，随机流推进次数不变） |
| 合练侧 | 结果蛊若已是同名仙蛊，拒绝合练并提示 `feedback.xianGuConflict` |
| 并发 | 仲裁与「首仙楼层」写入在同一临界区内完成，各联机端并发处理收敛到同一胜者 |
| 预览隔离 | 升炼**预览**走独立的 `TryIncreaseGuRankForPreview`（只改显示转数），否则预览会触发真实仲裁甚至降转别人的仙蛊 |

### 4.4 强化槽改用前置 MultiEnchantmentMod

0.8.0 的做法是自研复合载体占住 `CardModel.Enchantment`；本版改为**依赖前置**：

| 维度 | 0.8.0（自研载体） | 0.9.0（前置额外槽） |
| --- | --- | --- |
| 槽位 | 占用原版唯一主槽，内部再分「原生 + 强化」两项 | 前置在主槽之外旁路维护额外附魔槽 |
| 原版附魔 | 被接管进载体，`card.Enchantment is X` 判定在少数场景失效 | 照旧留在主槽，判定不受影响 |
| 挂载 | `CompanionEnhancementService.Attach` 自管槽位与层数 | `MultiEnchantmentApi.ForceEnchant`（单次调用内跳过 `CanEnchant => false` 的否决权） |
| 叠层 | 服务层自己夹取 `MaxAmount` | 前置的 `MergeAmount`，由 `CompanionEnhancementRegistration` 集中登记 |
| 卡面表现 | 9 个 Harmony 补丁点自绘第二页签 / 预览 / 特效 | 前置负责图标页签、钩子分发、提示与存读档 |
| 持久化 | 两个 `[SavedProperty]` JSON 字段（依赖前置库的属性注入补丁） | 前置的 `ToSerializable/FromSerializable` 后缀 |
| 遗留缺口 | `Claws` / `ThievingHopper` / `CloneRestSiteOption` 三条识别缺口 | 结构性消失 |

- `AbstractCompanionEnhancement.CanEnchant(card) => false` **保留**：强化仍绝不参与原版附魔来源（事件、遗物、篝火），但该否决权不会阻断本模组自己的 `ForceEnchant` 挂载。
- 登记**必须**集中做，不能靠 `[Enchantment]` 特性：前置的该特性是 `Inherited = false`，挂在父类上不会被子类继承，漏标注会**静默退化**成 `DisallowDuplicate`（不再叠层且不报错）。
- `OnPlay` 的执行策略改为 `HookExecutionMode.PerLiveInstance`：`MergeAmount` 默认 `MergedTotal` 会按层数各跑一次 OnPlay，那样"打出一次子卡"会扣掉与层数相同的可用次数。

### 4.5 父蛊→子卡强化的声明式管线

- **父蛊**（催动后授予强化的蛊牌）实现 `ICompanionEnhancementSourceGuCard`，只声明 `BuildCompanionEnhancementGrant()`（返回 `CompanionEnhancementGrant.Of<T>(层数)`，或 null 表示本次不授予）。未实现该接口的蛊牌催动时一次类型判断后直接返回，零开销。
- 催动管线 `GuZhenRenRubildRelic.BeforeCardPlayed` 在蛊牌正式结算前调用 `CompanionEnhancementService.ApplyDeclaredGrants`；授予目标经 `CompanionRelationshipService` 解析为该蛊配对的**全部**伴生牌，因此 `CompanionDefinition.Count > 1` 天然泛用。
- 首批两项：月光蛊 → `YueRenEnhancement`（每层月刃伤害 +2）、玉皮蛊 → `YuPiJiaEnhancement`（每层玉皮甲格挡 +3）；都是每次催动 +1 层、上限 3 层。
- **作用域固定 `EnchantmentScope.UntilCombatEnds`**：强化只活本场战斗、不镜像进牌组；下一场战斗必须由父蛊重新催动授予。战斗中找不到战斗副本（`ResolveAttachmentTarget` 按 `ReferenceEquals(candidate.DeckVersion, 永久实例)` 定位）就跳过挂载、不退回牌组实例。
- **原版钩子契约**：`EnchantDamageAdditive` / `EnchantBlockAdditive` 返回的是**增量**（分发侧 `result += 钩子(...)`），返回"原值 + 增量"会双倍计算。

### 4.6 强化的次数账本与生命周期

| 项 | 规则 |
| --- | --- |
| 声明方 | `AbstractCompanionEnhancement.UsesPerCombat`（0 = 不限，活到战斗结束）；首批两项均为 3 |
| 账本 | `CompanionEnhancementUses`：`ConditionalWeakTable`，按「战斗卡实例 + 强化类型」分账，纯运行时 |
| 计数点 | `OnPlay`（**sealed**，唯一的次数消耗入口）：先 `IsEffectTriggered` 判定，再 `OnEffectTriggered`，最后 `Consume` |
| 为什么在 OnPlay | 前置对额外槽的 `OnPlay` 派发发生在**子卡自身效果结算之后**，因此最后一次触发仍吃满加成 |
| 耗尽 | `Consume` 归零即 `RemoveEnchantment(..., ActivationLimitReached)`，卡面强化图标随之消失（「清空强化槽」） |
| 同场刷次数 | 已被账本堵住：同一场战斗内重新催动父蛊不会回满次数，只有下一场战斗重置 |
| 层数 vs 次数 | 层数（`Amount`）是强度、由父蛊多次催动叠加（`MaxAmount` 封顶）；次数是可用次数，两者独立 |
| 扩展点 | 带触发条件的强化覆写 `IsEffectTriggered`（例如只在子卡确实获得格挡时返回 true）；触发瞬间的附加行为覆写 `OnEffectTriggered` |

### 4.7 系统牌固定位（`IGuHandPinnedCard`）

- 接口只有一个成员 `GuHandOrderRank`：**升序**稳定排列在蛊手牌最左端。仙元牌秩 0、杀招推演牌秩 1。
- 悬停牌**不占补位槽**：`GuCardPileSystem.CountActiveGu` 只统计蛊牌，因此系统牌不会挤掉蛊牌的 5 个位置。
- 两张系统牌都重写了 `ModifyCardPlayResultLocation` 直接声明"回到蛊手牌原地"，不走 `GuCardRuntime.GetResultPile` 的使用次数/冷却循环；`CanBeGeneratedInCombat = false`、`MaxUpgradeLevel = 0`、带 `Retain` 关键词仅用于向玩家说明常驻。
- 杀招推演牌同时改为**自带催动次数**（三转起每场 1 次、八转起 2 次，只有推演成功才消耗；失败/取消不消耗），不再靠"再补发一张牌"表达八转的第二次。

### 4.8 伴生牌数量自定义与角色更名

- `CompanionDefinition(Type CardType, int Count = 1)`：来源蛊进入永久牌组时自动配出 `Count` 张；缺省 1 保持旧的单伴生行为不变。
- 角色类由 `GuZhenRenRubildCharacter` 更名为 `GuYueFangYuan`（文件同步重命名）。RitsuLib 的角色本地化 key 由类名推导（`{ModId}_CHARACTER_{类名大写蛇形}`），因此本次同步改了 4 张表：`localization/{zhs,eng}/characters.json` 全部键 + `ancients.json` 的 `NEOW.talk` / `DARV.talk`（其第二段内嵌角色 key 前缀）。

## 5. 战斗时序

★ 为本版新增或改动的环节。

1. **BeforeCombatStart**（遗物）：`ApertureSystem.HandleCombatStarting` 按运行层数重置本场进度；清掉残留杀招材料绑定。
2. ★ **BeforeHandDraw**（遗物）：先 `HandleShaZhaoDerivationGrantAsync`（三转起、杀招池非空时发推演牌），再 `HandleXianYuanGrantAsync`（六转起按转数发对应档位仙元牌）。两者都不占起手抽牌、不占蛊牌补位槽，且各自按运行层数去重（重连安全）。
3. **回合开始 / AfterEnergyReset**（遗物）：先恢复到期蛊牌，再按转数补元气（六转封顶 6 / 回复 3）。
4. ★ **可打出判定**：`GuCardRuntime.CanActivate` 接受激活区或原生手牌（原生手牌是出牌事务中的临时位置），**六转及以上还要求 `ImmortalEssenceSystem.CanPayActivation`**；被拦下时原版气泡台词由 `XianYuanWarningPatch` 换成「仙元不足，无法催动六转以上的蛊」。
5. ★ **打出蛊牌**：`BeforeCardPlayed` → 幂等 `MoveToNativeHand` → `GuCardRuntime.RegisterActivation` → `CompanionEnhancementService.ApplyDeclaredGrants`（父蛊给伴生挂强化）→ 六转起扣仙元单位 → 原生结算（元气照付）→ 仍有次数回激活区，耗尽进恢复区。
6. ★ **打出子卡**：前置对额外槽的 `OnPlay` 派发（在子卡自身效果结算之后）→ `AbstractCompanionEnhancement.OnPlay`（sealed）→ `IsEffectTriggered` → `OnEffectTriggered` → `Consume` 扣次数 → 扣到 0 立即移除强化。
7. ★ **系统牌打出**：仙元牌花 1 个单位把元气补满；杀招推演牌选目标杀招 → 选材料 → 支付额外元气 → 材料封入蛊封存区、杀招入手且首次打出免费。
8. ★ **卡牌进入永久牌组**：`Hook.ShouldAddToDeck` 后缀 → 仙蛊唯一仲裁（拒绝入牌或降转落败者）。
9. ★ **奖励生成**：`CardReward.Populate` 后缀 → 为新蛊牌抽初始转数（已有同名仙蛊则上限压到五转）→ 若已是仙蛊则 `RegisterXianGuClaim` 登记首仙楼层。
10. ★ **升转（升炼 / 合练）**：先过唯一性仲裁再提交转数；预览路径走无仲裁的 `TryIncreaseGuRankForPreview`。
11. **费用区渲染**（纯表现）：`NCardGuEnergyCostPatch` 为蛊牌改写费用数字/图标/配色。
12. ★ **蛊手牌布局**：固定位系统牌按 `GuHandOrderRank` 排在蛊手牌最左端，且不计入补位容量。

## 9. 已知限制与后续方向

1. **未做游戏内端到端验证**：本版只完成编译级 + 资源导出级 + 打包级验证（见第 10 节）。未启动游戏、未做任何存读档与联机验证。第 10 节与本条一致：本版没有任何实机结论。
2. **【最高优先】强化次数的账本是纯运行时状态**：`CompanionEnhancementUses` 用 `ConditionalWeakTable` 按战斗卡实例分账，不写存档。**战斗中途存读档**会重建战斗卡、账本随之清空，次数回满。若需要严格封死，应把账本改为随卡持久化。
3. **强化只在战斗中可见**：作用域固定 `UntilCombatEnds` 且不镜像进牌组；`CompanionRelationshipService.GetCompanions` 恒返回永久牌组实例，因此挂载时需要在战斗中按 `DeckVersion` 反向定位战斗副本（`ResolveAttachmentTarget`），**找不到战斗副本就跳过挂载**（例如在战斗外的牌组视图中催动不会有可见效果）。切勿牌组与战斗实例双挂，否则经 DeckSync 会重复合并叠层。
4. **原版附魔钩子的增量契约**：`EnchantDamageAdditive` / `EnchantBlockAdditive` 等加值钩子返回的是**增量**（分发侧 `result += …`），返回"原值 + 增量"会双倍计算。写新强化时按此契约。
5. **仙元只实现到九转**：十转及以上仍取黄杏仙元（面额 16）；`GetActivationCost` 的指数封顶在 2³ = 8。扩展十转以上必须先扩 `ApertureProgression` 的曲线与 `ImmortalEssenceSystem` 的映射。
6. **仙蛊唯一的边界**：未登记的既有仙蛊按"最早产生"处理（`int.MinValue`），因此**旧存档中手工/外部产生的六转以上同名蛊不会被新仙蛊顶替**；这是刻意选择的保守方向。仲裁范围是"整个 run 的全部玩家永久牌组"，不含战斗临时副本。
7. **杀招池仍为空**：杀招推演牌只在杀招池非空时发放（否则不发放），因此整条杀招链路在 0.9.0 仍**不会在正常游戏里被触发**。补一张带 `[ShaZhaoRecipe]` 的杀招牌即可启用。
8. **系统牌固定位不做容量占用**：`CountActiveGu` 只统计蛊牌，所以仙元牌与推演牌不会挤掉蛊牌的 5 个位置；代价是这两类牌完全不走牌堆循环，任何需要"从手牌移除/消耗"的原版效果对它们无效（它们由 `ModifyCardPlayResultLocation` 显式声明回到原地）。
9. **仙元不足提示的取舍**：当一张六转以上蛊牌**多因并存**（如次数耗尽 + 仙元不足）时，本补丁仍优先报仙元不足——仙元确属真实缺口即覆盖台词，不逐一区分首要原因，属有意为之（已写进补丁注释）。
10. **`XianYuanWarningPatch` 在 0.9.0 才接线**：该补丁在 `868f4ca` 就随仙元骨架入库，但直到本版才登记进 `Entry.RuntimeComponents`（提交 `9a34ae1`）——在此之前它是**死代码**，玩家的仙元不足提示不会出现。0.8.0 的发版记录把"登记该补丁"列为发版前置条件，本版完成。
11. **前置 MultiEnchantmentMod 是硬依赖**：玩家必须自行安装（Steam 创意工坊或自行构建），清单声明 `min_version = v2.5.4`，csproj 在编译期校验 DLL 存在。额外槽的图标页签、钩子分发、悬浮提示与**存读档持久化**全部由前置负责——因此强化的存读档正确性依赖前置版本，接入新强化后仍需一次实机「存 → 读档」验证。
12. **强化的实机表现未验证**：叠层显示、额外槽图标、`extraCardText` 追加、联机同步、以及首次触发后的移除时机，均只有静态与编译级证据。
13. **`Docs/模组新增内容总览.md` 的计数已随本版同步**（16 项组件 / 11 组补丁 / 9 张本地化表）；该文档描述的是 0.9.0 发布时的全量状态。
