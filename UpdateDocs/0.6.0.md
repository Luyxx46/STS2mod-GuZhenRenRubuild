## 1. 版本摘要

## 4. 核心玩法系统

### 4.1 配方匹配规则

- 配方声明在**结果牌**类型上：`[ShaZhaoRecipe(typeof(A), typeof(B), MinimumMaterialRank = n)]`，`AllowMultiple = true`。
- 材料必须是蛊牌（`IGuCard`），**材料数 ≥1**（与合练的 ≥2 不同：单张蛊也能是合法杀招配方）。
- 匹配按**无序多重集**：只比较类型与数量，玩家选择顺序无关；重复类型代表需要多张同名材料。
- 每条配方可单独要求 `MinimumMaterialRank`（默认 1），材料必须**逐张**达标。
- 同一结果牌可声明多条配方；同一批材料**不允许**同时命中两个不同结果——发现重复配方会在首次扫描（`Lazy<RecipeBook>`）时抛 `InvalidOperationException`。
- 配方册一次性建立三个索引：材料多重集 → 配方、结果类型 → 配方列表、材料类型 → 最宽松最低转数。

### 4.2 推演流程

1. **发放**：遗物 `BeforeHandDraw` 调用 `ApertureSystem.HandleShaZhaoDerivationGrantAsync`。条件为：空窍转数 ≥ 3、本运行层数尚未发放、且 `ShaZhaoRecipeRegistry.HasAnyRecipe` 为真。满足时由 `CombatState.CreateCard` 创建推演牌并经 `CardPileCmd.AddGeneratedCardToCombat` 直接入手，因此**不占起手抽牌**。
2. **候选材料**：只取**蛊手牌（激活区）+ 蛊待命堆**中 `GuCardRuntime.CanUse` 为真、且身上没有绑定记录的蛊牌；蛊冷却堆与蛊封存区不参与。
3. **目标选择**：把当前材料足以完成的杀招类型做成只读预览，进入 `CardSelectCmd.FromSimpleGrid` 网格（可取消，强制手动确认）。
4. **材料选择**：只显示与目标匹配的材料；数量上/下限由目标配方决定，上下限一致时不要求逐张确认。
5. **计费**：推演元气 = 全部材料 `YuanQiCost` 的算术平均值**向上取整**（整数除法 `(total + count - 1) / count`）。元气不足则弹窗并返回 false，不消耗任何资源。
6. **创建与封装**：`ShaZhaoRecipeRegistry.TryCreateResultForTarget` 用 `CombatState.CreateCard` 创建结果牌（必须走战斗状态创建，否则后续打出会因 `ContainsCard` 为假而抛异常），写入转数后 `AbstractShaZhaoCard.BindMaterialsAsync` 在 `ShaZhaoSynthesisScope` 内逐张封装材料：写绑定记录并把材料移动到蛊封存区，随后校验材料确实已进入封存区，未生效则撤销该张的封装记录。
7. **交付**：结果牌 `EnergyCost.SetUntilPlayed(0)`（首次打出免费）后加入手牌；元气在交付成功后才实际扣除，扣费失败会撤销已创建的结果牌。
8. **登记**：`ApertureSystem.RegisterShaZhaoDerivationAsync` 记录本场次数；八转起且次数未满上限时，再创建一张推演牌放入**弃牌堆**。
9. **失败路径**：取消、配方无效、材料不足、元气不足、无法创建、手牌已满 → 返回 false，推演牌回到手牌，并原额返还原生管线已支付的能量与星星。付费之后的封装阶段另有异常回滚：把元气恢复到扣费前的数值、收口已封装的材料、移除未交付的结果牌，再按"无法创建"失败处理。

### 4.3 杀招转数与生命周期

- 转数 = 材料的**最高转数**（`GetMaterialRank`：蛊牌取 `IGuCard.GuRank`，非蛊牌按 0）。杀招允许 **0 转**（尚未组方），与蛊牌的一转下限不同。
- 转数**不可被升炼提升**：`AbstractShaZhaoCard` 只提供受保护的 `SetGuRank`，不参与 `GuRankUpRules`（它根本不是蛊牌，不会出现在篝火升炼候选里）。
- `ShaZhaoLifecycle` 四型：`Instant` 用完即消耗；`Charged` 按 `ShaZhaoMaxUses` 扣次；`Staged` 按 `MaxStages` 推进；`Sealed` 视为封印结算后收口。具体杀招在自身 `OnPlay` 末尾调用 `AdvanceLifecycleAsync`。
- `MaterialsSealedPermanently = true` 的杀招在消耗时只清绑定记录、材料保持封存（不回冷却堆）。
- `OnShaZhaoComposed(orderedMaterials)` 收到按「类型名 → 转数降序 → 原始下标」稳定排序后的材料数组，可供顺序相关效果使用。

### 4.4 材料封装与返还

- 绑定关系分两侧记录（都是 `SavedAttachedState`，随存档与联机快照恢复）：材料侧记录"被哪一张杀招封装"，杀招侧记录"封装了几张"。
- **绑定键是战斗实例身份，不是模型身份**：同名杀招可以在同一场战斗里同时存在（八转起每场最多推演两次），因此键取自 `NetCombatCardDb` 的战斗卡编号（取不到时退回模型编号）。键在**首次封装时冻结**并写入附加状态后复用——如果每次现算，封装与收口两个时刻拿到的编号可能不同，绑定就会漂移、材料永远留在封存区；键与绑定计数同生命周期，收口时一起清空。
- **封装会校验结果**：把材料移进蛊封存区后重新检查其所在牌堆；若移动没有生效，立即撤销本次绑定记录与计数并记警告，避免留下"杀招计数大于零却找不到材料"的状态（那会让主动解体白扣 1 点能量）。材料没有归属玩家时同理，不会因为空引用中断整次推演。
- **返还**（正常用完 / 主动解体 / 异常移出）：材料解绑 → 移动到蛊冷却堆 → `GuCardRuntime.BeginRecovery(..., extraTurns: 1)`，即**从零开始完整冷却并额外延后 1 回合**。移动与冷却写入的顺序是"先移动、后写冷却"，移动失败时冷却不会被提前提交。
- **战斗结束**：只清绑定记录、不移动牌。材料留在原地，随战斗牌堆回收流程回牌组。**即使材料是"永久封存"也会在此解绑**，否则绑定字符串会跨战斗残留，使材料在下一场战斗被误判为"已被其他杀招封装"。清理以**材料侧记录**为准（遍历战斗内全部卡牌，而不是按杀招侧计数反查），因此即使某条返还路径被异常打断、两侧记录已经失配，也不会留下跨战斗的残留绑定；`MarkMaterialSealedAsync` 遇到残留绑定只记警告并覆盖，不抛异常中断推演。
- **战斗开始**：`ClearStaleBindings` 再清一次残留绑定（牌组 + 战斗内卡牌）。战斗卡编号会在新战斗里重新分配，残留的旧编号可能恰好被新战斗中的另一张牌占用，因此这一道兜底是必要的。
- **异常移出**：`ShaZhaoBindingPatch` 后缀监听 `CardPileCmd.RemoveFromCombat`；正常消耗路径会先自行解绑，因此后缀不会重复处理。用 `object[] __args` 读取卡牌，不依赖原方法形参名。
- **候选过滤**：推演候选除了"是蛊牌且仍可催动"之外，还要求**身上没有绑定记录**，因此即使某张材料因为异常没被移走，也不会被第二次封装。

### 4.5 主动解体

`ModRightClickRegistry.Register<CardModel>` 注册右键处理器（`priority: 100`，handler id `sha_zhao_dismantle`）。可解体条件：`Model` 是杀招、仍绑定材料、位于手牌、玩家在战斗中且能量 ≥ 1。执行时依次 `PlayerCmd.LoseEnergy(1)` → `FinalizeAsync(Dismantled)` → `CardCmd.Exhaust`。

### 4.6 与合练 / 升炼的关系

三者互相独立：合练与升炼是休息点选项（同一次休息点只能执行一次）；杀招推演是**战斗内**行为，由系统牌触发，不消耗休息点行动。

## 5. 战斗时序

1. **BeforeCombatStart**（遗物）：`ApertureSystem.HandleCombatStarting` 按运行层数去重，重置本场战斗的推演进度（`ShaZhaoDerivationGrantFloor = -1`、`ShaZhaoDerivationsThisCombat = 0`）；随后 `ShaZhaoBindingService.ClearStaleBindings` 清掉上一场战斗可能残留的材料绑定（扫牌组 + 战斗内卡牌）。
2. **BeforeHandDraw**（遗物）：若空窍 ≥3 转且杀招池非空，创建「杀招推演」并直接加入手牌（不占起手抽牌）。
3. **回合开始 / AfterEnergyReset**（既有逻辑，本次未改）：先恢复到期蛊牌，再按转数补元气。
4. **打出「杀招推演」**（`ShaZhaoTuiYan.OnPlay`，仅 `IsFirstInSeries`）：进入 4.2 的推演流程。成功 → `CardCmd.Exhaust` 消耗本牌；失败 → 返还能量/星星并把本牌放回手牌（`ModifyCardPlayResultLocation` 同时声明目标牌堆为手牌，双保险）。
5. **打出杀招**：具体杀招各自结算后在 `finally`/末尾调用 `AdvanceLifecycleAsync` → 达到终态时 `FinalizeAsync(Completed)` + `CardCmd.Exhaust`。
6. **右键杀招**：按 4.5 解体。
7. **战斗结束**：遗物 `AfterCombatEnd` → `ShaZhaoBindingService.FinalizeAllForCombatEnd` 清理该玩家全部材料绑定；同时卡牌被移出战斗时由补丁兜底返还。

## 9. 已知限制与后续方向

1. **未做游戏内端到端验证**：本版只完成编译级静态验证与本地化 JSON 校验（见第 10 节）。`CardCmd.Exhaust` 收口、材料进出封存区的牌堆同步、右键解体判定、原版播放收尾是否会把推演牌搬进弃牌堆，都需实机回归。
2. **杀招池为空，推演牌当前不会发放**：这是刻意设计——`HandleShaZhaoDerivationGrantAsync` 以 `ShaZhaoRecipeRegistry.HasAnyRecipe` 为前置条件，避免玩家每场战斗都拿到一张必然失败的系统牌。启用方式：新增一个继承 `AbstractShaZhaoCard`、标注 `[RegisterCard(typeof(GuZhenRenRubildShaZhaoCardPool))]` 与至少一条 `[ShaZhaoRecipe]` 的类，**不需要改任何注册表或系统代码**。因此本版杀招链路只能通过代码审查与后续内容版验证。
3. **旧模组仅有的三张具体杀招全部未移植**，原因是它们都依赖本仓库不存在的力道体系：
   - `HeiTianDaShouYin` 黑天大手印（Instant，2 费攻击）：配方 `群力蛊 + 拔山`、`群力蛊 + 倒海拔山`。倒海拔山本身是合练结果蛊，其配方还需要挽澜蛊。效果里还有"兽力虚影"计数项。
   - `ShangLiHuiTian` 伤力回天（Instant，1 费攻击）：配方 `苦力蛊 + 自力更生蛊`。**其机制除配方外几乎全部是原版 API**（HP 百分比伤势分档、单张牌最高实际伤害记录、一次性濒死免死回复），是本仓库后续最值得整块移植的一张；需要连 `ShangLiHuiTianPower` 与 3 个原版 Hook（`ShouldDie` / `AfterPreventingDeath` / `AfterCombatEnd`）一起搬。
   - `WanWo` 万我（Staged，1 费能力）：配方 `群力蛊 + 我力蛊`；效果完全建立在 `ILiDaoBeastGuCard`、`LiDaoPhantomSystem`、`WoLiXuYing`、`WoLiPhantomSystem`、`WoLiTempHpPower` 之上，在缺少这些类型时 `shadowCount` 恒为 1，外壳没有意义。
   - 六种材料（群力蛊 / 拔山 / 倒海拔山 / 苦力蛊 / 自力更生蛊 / 我力蛊）**没有一种出现在本仓库现有六张蛊牌中**。
4. **仙元分支未移植**：旧版推演费用分两支——材料最高转数 ≥6（仙元境界）时按转数消耗仙元且不扣元气，凡人境界才按材料元气平均值计费。本仓库没有仙元系统，因此统一使用元气平均值公式。
5. **联机确定性重解析未移植**：旧版在选牌界面暂停同步行动后，按 `NetCombatCardDb` 编号在每端重新解析材料实例（`GuZhenRenDeterminism.GetCardNetworkId`），以处理"同名蛊有多张"的确定性。本版的**绑定键已经是战斗实例编号**（同名杀招不会互相串味），但仍直接使用本地选中的卡实例，因此**联机场景下同名蛊的材料选择可能有分歧**。
6. **手牌容量豁免未移植**：旧版 `HandCapacityExemptionPatch`（约 13 KB transpiler 补丁）让「杀招推演」与力道虚影不占普通手牌上限，并修正原版"补到满手"的同步逻辑。本版推演牌会正常占用 1 个手牌位，即每场战斗实际起手少抽 1 张。
7. **蛊封存原因被简化**：旧版 `GuSealSystem` 有 `Training` / `ShaZhaoMaterial` 两种原因，便于炼力与杀招共用同一个封存堆而不互相误判。本仓库没有炼力系统，因此只保留"材料侧绑定记录 + 牌堆位置"两重判据，未移植独立的封存原因枚举。
8. **杀招标签与蛊屋未移植**：旧版所有杀招强制带 `ShaZhao` 标签，并可经 `SetGuHouse` 附加 `XianGuWu` / `FanGuWu`。本仓库没有任何 `CardTag` 使用面，因此相关代码整块删除，`GuHouse` / `OnGuHouseChanged` / `AdditionalShaZhaoTags` 不存在。
9. **材料顺序快照未持久化**：旧版把材料类型全名与各自转数编码进 `SavedAttachedState`（以换行分隔），以支持"A→B 与 B→A 不同效果"以及读档后还原顺序。本版 `InitializeFromMaterials` 仍把稳定排序后的材料数组交给 `OnShaZhaoComposed`，但**不写顺序快照**，因此具体杀招无法在读档后还原当时的选择顺序。
10. **`ShaZhaoSynthesisScope` 暂无消费者**：与 0.3.0 的 `HeLianScope` 情况相同，作用域已移植并在封装期间生效，但当前没有系统读取它（旧版供本命蛊忽略删牌惩罚）。保留是为了让后续系统能识别杀招封装消耗。
11. **配方图鉴 UI 未移植**：旧版 `RecipeCompendiumOverlay` 属独立模块。注册表已保留 `GetRecipeDetails()`，可直接供后续图鉴界面使用。
12. **推演费用读的是卡面 `YuanQiCost`**：旧版按 RitsuLib 已解析的元气支付计划（`SecondaryResourcePaymentResolver`）逐行求和，能正确处理 `CostsX`、费用修正等情形。本版直接读 `IGuCard.YuanQiCost`（本仓库所有蛊牌的该属性是固定值，无费用修正），因此若后续引入费用修正，需要改为读支付计划。
13. **杀招没有专属美术**：本次不含杀招牌，故无新增杀招卡图；推演牌卡图取自旧模组。
14. **主动解体没有重入保护**：`TryDismantleAsync` 依次做"检查绑定 → 扣能量 → 收口 → 消耗"。两次重叠的右键请求可能在计数被清空之前都通过检查，从而白扣 2 点能量（旧版同样没有这层保护）。属于低概率交互竞态，需要实机确认右键派发是否可能重叠后再决定是否加去重标记。
15. **既有代码的一处顺序问题（本次未改）**：`GuCardPileSystem.RestoreRecoveredCardsAsync` 会先调 `GuCardRuntime.CompleteRecovery` 清零恢复倒计时、再调用 `MoveCardToPileAsync`，而后者不检查牌堆命令的返回结果。若这次移动失败，蛊牌会既不"可恢复"又留在冷却堆，直到下一场战斗才被 `InitializeGuCardsForCombat` 收回。这是 0.5.0 就存在的行为，本次移植未触碰，仅在此记录；杀招材料的返还路径刻意采用相反顺序（先移动、后写冷却）。
