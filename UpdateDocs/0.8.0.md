## 1. 版本摘要

0.8.0 解决的是一个结构性限制：原版 `CardModel` **只有一个 `Enchantment` 字段**，因此「卡牌原本的原生附魔」与「我们想额外挂上去的强化」无法共存 —— 谁后写谁覆盖。本版用**复合附魔载体** `CompanionEnhancementSlot` 占用该物理字段，内部同时保存两项彼此独立的子附魔（原生附魔 + 强化），把两者的数值加成、战斗钩子、悬浮提示与状态汇总统一转发出去；卡面由补丁画出**第二个图标页签**。

载体**只在需要共存时才出现**：卡上原本没有附魔时强化直接占字段；只有卡上已有原生附魔时才转成载体；卸下强化后若仍有原生附魔，会还原成直接挂载的形态。这样原版里所有 `card.Enchantment is 某附魔` 的判定在绝大多数情况下仍然成立（已知例外见第 9 节第 3 条）。

同时提供**通用的挂载面**：`Attach` / `Attach<T>` / `Remove` / `ClearRegular`，以及「**催动蛊牌 → 给它的伴生牌挂强化**」的唯一入口 `AttachToCompanionOf`。

**本版功能在当前代码状态下不可被触发**：全仓库没有任何 `AbstractCompanionEnhancement` 的具体子类，也没有任何蛊牌调用 `AttachToCompanionOf`（见第 9 节第 5 条）。这是刻意的范围 —— 先把槽位与 API 做对，具体强化按蛊牌逐个定义。

除强化槽外，0.8.0 还一并收纳了 0.7.0 之后两次**未单独发版**的改动：**六转进入仙窍后元气停止成长**（容量封顶 6、每回合恢复封顶 3）与**移除杀招右键解体功能**。本文件第 2～8 节只详述强化槽，那两项的归属见第 3.3 节与附录。

## 4. 核心玩法系统

### 4.1 为什么必须是「复合载体」

原版 `CardModel` 只有一个 `Enchantment` 字段（`sts2/src/Core/Models/CardModel.cs:631`），`NCard` 也只有一个 `%Enchantment` 页签。前置库 RitsuLib 0.5.18 **没有**多附魔槽 API（只有 `ModEnchantmentTemplate`、`[RegisterEnchantment]` 与图标覆盖）。因此要让「原生附魔」与「强化」共存，只能自己占用该字段并把两项子附魔一起保存、一起转发。

实现方式取自旧模组的「血寄」复合附魔（`XueDaoCompositeEnchantment` + `XueDaoEnchantmentSlotPatch`），但**已通用化**：解析逻辑按运行时类型判断，不硬编码任何具体附魔类型或载体形态。

### 4.2 载体语义

| 场景 | 行为 |
| --- | --- |
| 卡上无附魔 + 挂强化 | 直接让**载体**占住字段（`ClearEnchantmentInternal` → `EnchantInternal(slot, 1)`） |
| 卡上已有原生附魔 + 挂强化 | 先摘原生附魔 → 载体占字段 → `ImportExisting` 把原生附魔接管进载体 |
| 卸下强化、仍有原生附魔 | 载体摘下 → 原生附魔**还原成直接挂在卡上**的形态，层数保留 |
| 只清原生附魔 | `ClearRegular`：只摘原生栏位，强化与载体保持不动 |
| 两项都没有 | 不应出现；载体自身的图标仅作为兜底 |

- 载体 `ShowAmount = false`、`HasExtraCardText = false`、`DisplayAmount = 1`、`CanEnchant(card) = false`（禁止原版把载体本身当附魔施加）。
- **载体 `Amount` 恒为 1** 是一条被显式维护的不变式：载体的 8 个写入口（两个 `[SavedProperty]` setter、`OnEnchant`、`ImportExisting`、`AddOrStackRegular`、`AttachEnhancement`、`DetachRegular`、`DetachEnhancement`）都会把它复位为 1。
- 载体状态 = 两项子附魔的汇总：**任一项为 `Normal` 则载体为 `Normal`**，否则 `Disabled`。

### 4.3 强化槽 API（`CompanionEnhancementService`）

| 入口 | 说明 |
| --- | --- |
| `HasSlot(card)` | 卡牌当前是否由载体承载附魔 |
| `TryGetEnhancement(card)` / `TryGetRegular(card)` | 分别读取强化 / 原生附魔栏位 |
| `TryGetRegular<T>(card, out T)` | 按具体类型读原生栏位（**预留**，当前无调用方） |
| `EnumerateEnchantments(card)` | 按「原生 → 强化」枚举全部附魔（**预留**，当前无调用方；补丁直接读载体字段） |
| `Attach(card, enhancement, amount)` | 挂载强化；返回实际生效的实例 |
| `Attach<T>(card, amount)` | 按类型挂载（内部 `ModelDb.Enchantment<T>().ToMutable()`） |
| `Remove(card)` | 卸下强化；返回是否真的卸下 |
| `ClearRegular(card)` | 只清原生附魔栏位 |
| **`AttachToCompanionOf(sourceGu, enhancement, amount)`** / `AttachToCompanionOf<T>(sourceGu, amount)` | **催动蛊牌 → 给它的伴生牌挂强化** 的唯一入口 |

**拒绝规则（返回 `null` 且不改动卡牌，只记一条 `Warn`）**

| 条件 | 日志 reason |
| --- | --- |
| 目标不是伴生牌（非 `ICompanionCard`） | `NotCompanionCard` |
| 传入的强化实例已经绑定在别的卡上 | `EnhancementAlreadyAttached` |
| 槽内已有**不同类型**的强化（一个槽只放一项） | `SlotHoldsSingleEnhancement` |
| `AttachToCompanionOf` 找不到伴生牌（不在牌组 / 未配对 / 非伴生来源蛊） | `NoCompanion` |

**叠加与封顶**：同类型强化按层叠加，`Amount = min(MaxAmount, Amount + amount)`；`amount` 下限为 1。挂载与卸下之后都会执行 `DynamicVars.RecalculateForUpgradeOrEnchant()` + `FinalizeUpgradeInternal()`。

### 4.4 强化父类与子类约定（`AbstractCompanionEnhancement`）

| 成员 | 默认 | 说明 |
| --- | --- | --- |
| `ShowAmount` | `true` | 数量即层数，画在强化那一格的图标上 |
| `HasExtraCardText` | `false` | 需要卡面追加正文的子类自行覆盖为 `true`，并写 `<id>.extraCardText` |
| `CanEnchant(card)` | `false` | 强化**绝不参与原版附魔来源**（事件、遗物、篝火等） |
| `MaxAmount` | `int.MaxValue` | 叠加上限，需要封顶的强化覆盖此属性 |

子类可用的钩子集合 = 载体转发的那一批（4.5）。图标的约定是 `GuZhenRenRubild/images/enchantments/<类名>.png` 并自行覆盖 `CustomIconPath` / `AssetProfile` —— **基类不替子类猜路径**，以免指向不存在的资源而干扰预加载。

### 4.5 载体转发的钩子（17 个）

| 类别 | 钩子 |
| --- | --- |
| 数值 | `EnchantBlockAdditive` / `EnchantBlockMultiplicative`、`EnchantDamageAdditive` / `EnchantDamageMultiplicative`、`EnchantPlayCount` |
| 流程 | `OnEnchant`、`RecalculateValues`、`OnPlay`、`AfterCardPlayed`、`AfterCardDrawn`、`AfterAutoPrePlayPhaseEntered`、`BeforeFlush`、`ModifyShuffleOrder` |
| 显示 / 判定 | `ShouldStartAtBottomOfDrawPile`、`ShouldGlowGold`、`ShouldGlowRed`、`ExtraHoverTips` |

- 格挡与伤害按**逐项「先加后乘」**累加（与旧版复合载体一致）；`OnPlay` / `AfterCardPlayed` 每项之后调用 `InvokeExecutionFinished()`，与原生单附魔路径的簿记一致。
- `ShouldStartAtBottomOfDrawPile` 在卡牌自带 `Innate` 时直接返回 `false`（与原版语义一致）。
- 克隆（`DeepCloneFields`）会深拷贝两项子附魔并把订阅表换成**新列表** —— `MemberwiseClone` 会共享同一个 List 实例，否则清理克隆体时会把原件的订阅一起清掉。

### 4.6 原版直写 `Amount` 的兼容通道

原版有少数附魔**绕过钩子链**，在 `AfterCardPlayed` 里直接对「持久侧附魔实例」自增层数 —— 典型是 `Goopy`（`sts2/src/Core/Models/Enchantments/Goopy.cs:30-42`：先给战斗实例 `Amount++`，再对 `Card.DeckVersion.Enchantment.Amount++`）。

当 `Goopy` 这类附魔落在本载体的**原生栏位**时，`DeckVersion.Enchantment` 就是**载体本身**，于是持久侧永远不涨、载体 `Amount` 反被顶成 2/3/…。载体的处理是**整支跳过转发**而不是「转发后再纠正」（转发已经写错载体 `Amount`，纠正无法把战斗实例的自增补回正确语义），改为把这套双写等价地分别落到：

1. **战斗实例**：`goopy.Amount++` + `RecalculateValues()`；
2. **持久侧同类型内层**：私有助手 `TryIncrementDeckVersionInner` 按运行时类型解析出持久侧的 `Regular` 或 `Enhancement` 并自增，**绝不写载体**；解析不到就静默返回，不抛异常。

> 可达性提示：`Goopy.CanEnchant` 要求卡牌带 `CardTag.Defend`，而当前两张伴生牌都没有声明 `CanonicalTags`，因此这条通道目前**打不出来**（见第 9 节第 5、6 条）。

### 4.7 卡面第二页签

`NCard.UpdateEnchantmentVisuals` 的前缀会先清理旧页签，再按「原生附魔 → 强化」决定画几个：只画主项时沿用原版页签；两项都在时**复制一个 `%Enchantment` 节点**（统一以 `GuZhenRenRubildEnhancementTab` 为名前缀，便于按前缀清理）叠在下方。图标、数量与禁用态沿用原版的着色逻辑（同一组 shader 参数 `h` / `s` / `v`）。页签位置基于 `NCard._defaultEnchantmentPosition` 加纵向间距。

附魔预览（`NEnchantPreview.Init`）与附魔特效（`NCardEnchantVfx._Ready`）同样接管：预览副本必须保留强化槽（原生 `Init` 会整个覆盖附魔字段），特效节点则同步第二个图标。

## 5. 战斗时序

本版**未改动战斗流程**，新增的都是「附魔层」的钩子转发与「表现层」的页签绘制。按时机列出全链路如下（★ 为本次新增）：

1. **BeforeCombatStart**（遗物）：重置本场杀招推演进度；清理残留材料绑定。
2. **BeforeHandDraw**（遗物）：空窍 ≥3 转且杀招池非空时发放「杀招推演」。
3. **回合开始 / AfterEnergyReset**（遗物）：先恢复到期蛊牌，再按转数补元气。
4. **原版可打出判定 / 自动打出判定**：`GuCardRuntime.CanActivate` 同时接受激活区与原生手牌。
5. **打出蛊牌**：支付元气 → 结算效果 → 仍有次数回激活区，次数耗尽进恢复区。
6. ★ **打出带载体的卡**（仅当卡上同时存在原生附魔与强化时才有实际差异）：`OnPlay` → 原生附魔 → 强化，逐项转发并各自 `InvokeExecutionFinished()`。
7. ★ **打出后钩子**：`AfterCardPlayed` 逐项转发；若内层是 `Goopy`，走 4.6 的双写兼容通道而不是直接转发。
8. ★ **抽牌 / 自动前置阶段 / 回合结束弃牌 / 洗牌**：`AfterCardDrawn`、`AfterAutoPrePlayPhaseEntered`、`BeforeFlush`、`ModifyShuffleOrder` 逐项转发到两项子附魔。
9. ★ **数值结算**（格挡与伤害）：载体把两项子附魔的加/乘钩子串起来（先加后乘），因此强化的数值加成与原生附魔叠加生效；打出次数由 `EnchantPlayCount` 逐项串接。
10. **费用区渲染**（纯表现）：`NCardGuEnergyCostPatch` 为蛊牌改写费用数字/图标/配色。
11. ★ **卡面渲染**（纯表现）：`UpdateEnchantmentVisuals` 画第二个图标页签；`GetDescriptionForPile` / `GetDescriptionForUpgradePreview` 追加两项子附魔的 `extraCardText`；`HoverTips` 拼出「强化槽 → 原生附魔 → 强化」。
12. **战斗外**：顶栏按钮打开蛊方大全（只读）。

## 9. 已知限制与后续方向

1. **未做游戏内端到端验证**：本版只完成编译级验证（见第 10 节）。未启动游戏、未导 PCK、未做任何存读档。第 10 节与本条一致：本版没有任何实机结论。
2. **【最高优先】强化槽的持久化依赖前置库注入**：载体用两个 `[SavedProperty]`（`SavedEnhancementJson` / `SavedRegularJson`）持久化，而属性名需要 RitsuLib 的 `SavedPropertiesTypeCacheInjectionPatch` 把本类型注入 `SavedPropertiesTypeCache`。若未注入，`SavedProperties.FromInternal` 走 `GetJsonPropertiesForType(type) ?? new List<PropertyInfo>()`，会**静默写出零个属性** —— 于是**单机**存读档即丢失强化及其包着的原生附魔（不只是联机路径）。缓解依据：RitsuLib 0.5.18 确有该注入补丁，且旧模组在**同一 RitsuLib 版本**上用完全相同的 `[SavedProperty]` + JSON 字符串模式且已上线。⇒ **接入第一个具体强化子类后，必须做一次实机「存 → 读档」验证。**
3. **三条原版兼容缺口**：载体占住 `CardModel.Enchantment` 后，若卡牌的**原生**附魔是特定类型，原版这几个系统会识别不到它 —— `Claws`（远古遗物·变形，`sts2/src/Core/Models/Relics/Claws.cs:47-61`：拿到的是载体，`CanEnchant` 为 `false`，整段跳过）；以及本次**明确未移植**的 `ThievingHopper`（窃取稀有度分桶）与 `CloneRestSiteOption`（篝火复制）。旧模组为前两者写过专门补丁，本版按范围取舍未移植。**失败方向是安全的**（静默跳过，不抛异常、不脏数据），可达性窄。
4. **附加强化后不会立即重绘卡面**：`EnsureSlot` 触发卡牌事件时载体尚无内层，页签被置为隐藏；随后写入强化只改字段与载体状态（状态变化只改着色，不改可见性），因此第二个页签要等下一次 `NCard.UpdateVisuals`（悬停、换堆、重排等）才出现。会自愈、不崩。干净的修法需要重排「先让内层就位再挂到卡上」，风险高于收益，留给首个具体强化落地时做。
5. **本版功能不可被触发**：全仓库**没有任何 `AbstractCompanionEnhancement` 的具体子类**，也**没有任何蛊牌调用 `AttachToCompanionOf`**；因此强化槽在当前代码状态下永远不会被建立（`Goopy` 兼容通道也因此不可达）。这是刻意的范围 —— 本版只交付通用槽与 API。
6. **实机完全未验证的部分**：卡面第二页签的排版与刷新时机、两个槽同时存在时的附魔预览与附魔特效、`NCard` / `NEnchantPreview` / `NCardEnchantVfx` 的 10 个私有成员在真实装配下的反射解析、以及跨存档与联机同步。第 10 节列出的验证均无法覆盖这些。
7. **仙元 / 仙窍体系正在开发中**，本版**未包含**、也未接线（`Cards/XianYuan/`、`Cards/Core/ImmortalEssence/`、`AbstractXianYuanCard`、仙元卡池与警告补丁均未进入本版对应的提交，且其发放路径尚未实现）。本版不应对它作任何可用性声明。
8. **`AbstractCompanionEnhancement` 的钩子集合受限于载体的转发清单**：子类只能使用第 4.5 节列出的 17 个钩子；若后续强化需要其它附魔钩子（例如 `AfterCombatEnd`、`AfterEnergyReset` 等），必须先扩展载体的转发，再写子类。
