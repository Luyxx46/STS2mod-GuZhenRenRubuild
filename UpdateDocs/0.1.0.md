## 1. 版本摘要

0.1.0 完成了一条以「蛊」为核心的完整玩法链路：一个自定义角色、一种战斗内副资源（元气）、三个蛊牌专用牌堆、蛊转（品阶）成长与篝火「升炼」，以及作为蛊牌衍生牌的「伴生牌」体系。

| 系统 | 状态 | 一句话说明 |
| --- | --- | --- |
| 角色与卡池 | ✅ 可用 | 模板角色 + 专属蛊牌池 / 辅助卡池 / 遗物池 / 药水池 |
| 元气（副资源） | ✅ 可用 | 上限 5，首回合补满、此后每回合 +2，仅战斗内持久化 |
| 蛊牌三牌堆 | ✅ 可用 | 蛊手牌（激活区，5 位）→ 蛊待命堆 → 蛊冷却堆 → 循环回待命堆 |
| 蛊转（品阶） | ✅ 可用 | 1–9 转，奖励入手时按楼层高斯抽样，写入存档并参与联机同步 |
| 篝火「升炼」 | ✅ 可用 | 每次 2 槽；六转以下 1 槽、六转及以上 2 槽，带原生升级式绿色差异预览 |
| 伴生牌体系 | ✅ 可用 | 蛊牌可永久绑定一张普通伴生牌，配对持久化 + 自动修复 + 删除保护 + 联机映射 |
| 奖励池规则 | ✅ 可用 | 本角色卡牌奖励只出现真正的蛊牌，且不展示空奖励界面 |
| 起始遗物 | ✅ 可用 | 「一转空窍」：战斗开始 5 元气、此后每回合恢复 2 点，并挂接全部蛊牌时机 |

## 4. 核心玩法系统

### 4.1 元气（副资源）

| 项 | 值 |
| --- | --- |
| 编号 | `yuan_qi`（全局编号由 RitsuLib 加模组命名空间生成） |
| 初始值 / 下限 | 0 |
| 基础上限 / 硬上限 | 5 / 5 |
| 回合开始自动恢复 | 无（由遗物显式管理） |
| 持久化范围 | 仅当前战斗（`Combat`） |
| 恢复规则 | 第 1 回合直接补满；之后每回合 +2，不超过上限 |

- 战斗界面计数器：52×52 外框、46×46 图标、字号 20、描边 4、数量变化有增长动画。
- 位置：挂到原生能量计数器节点下的固定偏移 `(96, -102)`，即能量球右上侧；对目标角色战斗界面始终显示。
- 图标资源：`images/characters/energy_big.png`（大图）、`energy_text.png`（文本）。

### 4.2 蛊牌三牌堆与循环

| 牌堆 | 本地编号 | 界面样式 | 容量 / 位置 |
| --- | --- | --- | --- |
| **蛊手牌**（激活区） | `gu_active` | 额外手牌（可直接打出，显示可打出高亮） | 最多 **5** 张 |
| **蛊待命堆**（储备区） | `gu_storage` | 左下角主位，图标 `GuStoragePile.svg` | 无上限 |
| **蛊冷却堆**（恢复区） | `gu_recovery` | 左下角副位，偏移 `(-200, 0)`，图标 `GuRecoveryPile.svg` | 无上限 |

三个牌堆均为**仅战斗存在**（`CombatOnly`），牌堆悬浮说明见 `static_hover_tips` 本地化。

**循环**：`蛊待命堆 → 蛊手牌 → （次数耗尽）蛊冷却堆 → （冷却结束）蛊待命堆`

- 催动后仍有余次 → 回到蛊手牌；次数耗尽 → 送入冷却堆并记录「可恢复回合 = 当前回合 + 2」。
- 每回合能量重置后：先把到期蛊牌重置为完整可用并送回待命堆，再从待命堆首部补满蛊手牌。
- 补位为逐张异步移动，底层移动失败即停止循环并记录警告，避免同一张牌无限重试。
- 战斗开始时：把所有牌堆中的蛊牌清空战斗状态并**统一收入待命堆**，同时记录待命堆前 5 张作为「开场蛊」。

**开场入场**：原生本回合首次抽牌（`fromHandDraw = true` 且第 1 回合）完成之后，开场蛊才逐张带入场动画进入蛊手牌，从而不与原生首抽的界面流程抢占时序。

**本地/联机一致性**：本地点击蛊手牌时框架会先把卡移入原生手牌，而远端客户端重放同一动作没有这步界面事务，因此打牌前补做一次幂等移动（仅在卡仍位于激活区时执行）。

### 4.3 蛊转（品阶）

- 取值范围 **1–9 转**，读写均被夹紧在合法区间。
- 双轨状态：本地字段保证「对象克隆」后立即正确；`SavedAttachedState`（`gu_rank` / `gu_rank_assigned`）负责存档与联机同步。
- **初始转数**在卡牌首次进入奖励时抽取：
  - 均值 = `clamp(1.0 + (总楼层 - 1) × 0.05, 1.0, min(3.0, 最高转数))`；
  - 标准差固定 `2.0`，采样区间 `[0.5, 9.5]`，四舍五入取整；
  - 随机流与玩家、模组、固定流名 `reward/gu_rank` 绑定，**相同游戏状态下结果可稳定复现**；
  - 已被随机过的蛊牌不会重复消耗随机数（奖励界面重建时结果不变）。
- 转数变化会触发 `OnGuRankChanged` 钩子，由具体蛊牌刷新伤害/格挡等派生数值；读档反序列化后同样会重算。

### 4.4 篝火「升炼」

| 项 | 值 |
| --- | --- |
| 选项标识 | `GU_ZHEN_REN_RUBILD_GU_RANK_UP`（中文名「升炼」/ 英文 `Gu Refinement`） |
| 每次槽位预算 | **2 槽** |
| 槽位消耗 | 转数 < 6 → **1 槽**；转数 ≥ 6 → **2 槽** |
| 可选条件 | 牌组中的蛊牌且转数 < 最高转数 |
| 交互 | 逐张单选、需手动确认、可取消；直到槽位不足或无合法候选为止 |
| 可用性 | 牌组中至少有一张可升炼蛊牌时选项才可用 |

- 该选项**替代**了此前的 `GuRankUpgradePatch`（0.1.0 中已删除），使蛊转提升完全独立于原生升级。
- **预览**：在升炼选择作用域内，把原生「升级预览」映射为「转数 +1」，并把升转后新增或变化的卡面文本标绿（基于 LCS 差异比对，保留 BBCode 标签结构，连续空白的着色会被合并，避免英文逐词断开的绿色片段）。作用域外不改变原生升级行为对蛊牌的限制。
- **视觉反馈**：本地玩家播放原生铁匠特效（挂在卡牌预览容器），远端玩家在角色节点上播放。

### 4.5 伴生牌体系

**定位**：蛊牌可以拥有一张**永久绑定的普通牌**。伴生牌是标准卡牌 —— 使用普通能量、走原生抽牌堆/手牌/弃牌堆、可原生升级与附魔；它不属于蛊牌运行时，也不会被战斗内随机生成器凭空生成，归属辅助卡池。

**配对身份**

- `PairId`：`SavedAttachedState`（`companion_pair_id`，≥ 0）持久化，**是唯一写入存档的身份**。
- 网络编号（`DeckIndex` / `CombatCardId`）**只在运行时缓存，绝不写入存档**。
- 运行时映射按玩家隔离（`ConditionalWeakTable`），分永久牌组映射与战斗映射两组（正/反向）。

**自动修复 `ReconcileDeck`（唯一业务入口）**：在永久牌组增删、Transform、新游戏、读档、联机同步、战前等边界调用，且带可重入保护。

1. 修复来源蛊牌的 `PairId`：缺失或重复时按「永久牌组顺序」确定性分配新编号（从当前最大值 +1 开始），不使用随机值或 Guid；
2. 为每个来源寻找匹配的伴生：先匹配「同类型 + 同 PairId」，否则**优先复用未绑定/孤儿的同类型伴生**（迁移旧存档时保留其升级与附魔），再否则新建并插入到来源牌之后，继承来源的「加入牌组楼层」；
3. 删除没有来源的受管伴生（孤儿）；
4. 牌组若发生变化则广播内容变更，随后重建永久牌组映射。

**Transform 迁移**：变换前快照 `PairId` 与伴生实例；若新牌仍是同类型来源蛊牌 → 转移 `PairId`、保留原伴生实例（升级与附魔不丢）；若新牌不再需要伴生或需要不同类型 → 旧伴生移除、`PairId` 归零。

**删除保护**：伴生牌对玩家侧不可移除（`IsRemovable = false`），并从牌组删除指令中过滤受管伴生（拦截时记录警告与数量）。系统内部级联创建/删除通过 `AsyncLocal` 作用域计数器豁免保护，支持异步与嵌套调用。

**联机映射重建**：战斗开始（网络编号分配完成）后重建战斗映射，使「来源蛊牌 ↔ 伴生牌」在战斗牌堆中仍可互相解析；映射建立时会输出 `[Companion/CombatMap]` 日志便于排查。

### 4.6 奖励池规则

- 本角色（`GuZhenRenRubildCharacter`）的卡牌奖励候选**只允许蛊牌**出现。
- 过滤**只作用于奖励生成调用链**（通过 `AsyncLocal` 深度标记限定作用域），不污染 Transform、药水与战斗内生成。
- 奖励候选为空时直接返回空结果，不使用空奖励界面占位；`Hook.TryModifyCardRewardOptions` 阶段再兜底清除非蛊牌项。
- 候选数量会与合法候选数取小，避免请求数超过池内合法牌数。

## 5. 战斗时序（0.1.0 行为）

| 时机 | 行为 |
| --- | --- |
| 战前（战斗状态构建前） | 修复永久配对（`ReconcileDeck`） |
| 战斗状态构建后 | 刷新原生牌堆中蛊牌的转数派生数值 |
| 网络战斗编号分配完成 | 重建战斗配对映射 → 蛊牌全部收入待命堆 → 记录开场蛊（前 5 张） |
| 第 1 回合首次抽牌完成后 | 开场蛊逐张带入场动画进入蛊手牌 |
| 催动蛊牌前 | 幂等移入原生手牌 → 登记一次使用 |
| 催动蛊牌后 | 按剩余次数回蛊手牌或入冷却堆 → 从待命堆补满蛊手牌 |
| 每回合能量重置后 | 到期蛊牌恢复并回待命堆 → 补满蛊手牌 → 补元气（首回合补满，其后 +2） |
| 篝火 | 注入「升炼」选项，按槽位规则逐张提升转数 |
| 卡牌奖励生成 | 只出蛊牌；新蛊牌抽取初始转数；清除空奖励 |

## 6. Harmony 补丁清单

所有补丁均使用独立 `HarmonyId`（`GuZhenRenRubild.<组名>`）以便精确卸载。目标方法缺失时会**立即抛出异常**，使游戏版本不兼容在启动阶段暴露。

| `GuCombat` | `Player.PopulateCombatState` | 前置 + 后置 | 战前修复配对；战后刷新转数派生值 |
| `GuCombat` | `NetCombatCardDb.StartCombat` | 后置 | 重建战斗映射 + 收拢蛊牌 + 记录开场蛊 |
| `GuCombat` | `CardPileCmd.DrawInternal` | 后置 | 包装返回任务，第 1 回合首次抽牌后播放开场蛊入场（校验返回类型） |
| `CompanionDeckLifecycle` | `CardPileCmd.Add` | 前置 + 后置 | 卡牌进入永久牌组后修复配对 |
| `CompanionDeckLifecycle` | `CardPileCmd.RemoveFromDeck` | 前置 + 后置 | 记录受影响玩家，删除后修复配对 |
| `CompanionDeckLifecycle` | `CardCmd.Transform` | 前置 + 后置 | 变换前快照配对，成功后迁移或终结伴生 |

| `CompanionDeckLifecycle` | `Player.SyncWithSerializedPlayer` | 后置 | 联机同步后修复配对 |
| `CompanionMutationProtection` | `CardModel.IsRemovable`（属性读取） | 后置 | 受管伴生对玩家不可移除 |

| `GuRankUpPreview` | `CardModel.UpgradeInternal` | 前置（Priority.First） | 作用域内把「升级一次」实际执行为「转数 +1」并触发原生升级事件 |
| `GuRankUpPreview` | `CardModel.GetDescriptionForUpgradePreview` | 后置 | 升转后差异文本染绿 |

**模组入口生命周期**：内容注册（Godot 脚本 + 类型发现）只执行一次；8 个运行时组件按依赖顺序初始化，任一失败则**逆序回滚**已启动组件（单个回滚失败只记录警告，不覆盖原始异常）：

`GuCardPileSystem` → `YuanQiSystem` → `CompanionDeckLifecyclePatch` → `CompanionMutationProtectionPatch` → `GuCardRewardPatch` → `GuRankRewardPatch` → `GuRankUpPreviewPatch` → `GuCombatPatch`

```
GuZhenRenRebuild/

│  ├─ localization/{zhs,eng}/  # 7 张本地化表

│  ├─ Cards/                   # Core（蛊牌基类/运行时/牌堆/规则）、具体蛊牌、Companions
│  ├─ Characters/              # 角色与四个池
│  ├─ Combat/                  # YuanQiSystem（元气）
│  ├─ Patches/                 # 7 组 Harmony 补丁
│  ├─ Relics/ RestSite/        # 起始遗物、篝火升炼选项
├─ UpdateDocs/                 # 本更新日志目录
├─ GuZhenRenRubild.json        # 模组清单
├─ project.godot / .sln / .csproj
```

**构建流程**

1. 复制 `local.props.template` 为 `local.props`，填写 `Sts2Dir` 与 `GodotExe`；
2. `dotnet build`：编译 DLL，并复制 `GuZhenRenRubild.dll` 与清单到 `$(Sts2Dir)\mods\GuZhenRenRubild\`；
3. PCK 由 `GodotExe --headless --export-pack "Windows Desktop"` 导出（导出预设排除 `GuZhenRenRubild.json`）；
4. 清单中的 RitsuLib 依赖版本会在构建时与 NuGet 包版本自动同步；
5. 构建前校验 `sts2.dll` 是否存在，缺失时给出明确错误而不是编译报错。
