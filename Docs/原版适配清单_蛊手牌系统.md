## 1. 新蛊手牌系统在原版侧的真实形态

三条机制事实决定了全部适配面：

**S1｜蛊牌不在原生手牌堆。**
战斗内蛊牌位于 RitsuLib 注册的额外手牌（激活区 `gu_active`）+ 储备区 `gu_storage` + 恢复区 `gu_recovery` + 封存区 `gu_sealed`
（`GuCardPileSystem.cs:66-147`，`Style = ExtraHand`、`AllowCardPlay = true`、`Behaviors` 未设置 ⇒ 默认 `None`）。
原生"手牌"是 `PlayerCombatState.Hand`（`PlayerCombatState.cs:60`），两者互不包含。

**S2｜RitsuLib 把 4 个战斗牌堆追加进 `AllPiles`。**
`PlayerCombatState.AllPiles` 原本写死 5 堆（`PlayerCombatState.cs:70-82`），被 `ModCardPileAllPilesPatch` 追加模组堆，
因此 `AllCards => AllPiles.SelectMany(...)`（`:82`）与所有 `AllCards` 系效果**自动包含蛊牌**。

**S3｜战斗内蛊牌是牌组牌的克隆。**
`Player.PopulateCombatState` 用 `state.CloneCard` 把牌组牌克隆进战斗牌堆（`Player.cs:802-806`），
战斗结束 `PlayerCombatState.AfterCombatEnd()` 清空全部 `AllPiles`（`:142-151`）⇒ 蛊牌本体始终留在牌组（Run Deck），跨战斗不丢。

## 2. RitsuLib 已接管的原版落点（本模组无需再改）

| --- | --- | --- |

| `PlayerCombatState.HasCardsToPlay`（`:276-279`）、`NEndTurnButton.HasPlayableCard`、`NPlayerHand.FlashPlayableHolders` | `ModExtraHandQueryPatch` 转译 | "无牌可打"高亮/闪烁包含额外手牌 |
| `CardModel.get_Pile` / `CardModel.CanPlay` / `NHandCardHolder.UpdateCard` | `ModExtraHandSemanticPatches`：求值期间让额外手牌读到"原生手牌" | 这是蛊牌可打出的前提（历史坑见 memory：`CanActivate` 必须同时接受激活区与 `PileType.Hand`） |
| `NCardPlayQueue` / `PlayCardAction` 手动出牌链 | `ModExtraHandCardPlayPatch` + `ModExtraHandPlayCoordinator` | 取消出牌时把卡节点退回来源额外手牌 |
| 牌堆按钮/悬浮提示/布局/入场动画/多人同步 | `ModCardPile*` 系列补丁与 `ModCardPileInjector` | 含 `ModCardPileGetPatch`、`ModCardPileIsCombatPatch`、`ModCardPileFindOnTablePatch` 等 |

依据：`STS2-RitsuLib/src/CardPiles/Patches/`（`ModExtraHandHandViewPatches.cs`、`ModExtraHandQueryPatch.cs`、`ModExtraHandSemanticPatches.cs`、`ModExtraHandCardPlayPatch.cs`）与 `ModExtraHandHandView.cs`。

> `PlayerCombatState.Hand`，都只看到原生手牌（§3）；任何读 `AllCards` 的代码都会看到蛊牌（§4）。

### 6.6 "给牌"类事件走 `CardFactory.CreateForReward` 时的两个缺口 🔧

走 `CardFactory.CreateForReward` 的事件/遗物会命中模组补丁 `GuCardRewardPatch`（`:33-126`）：
- 对古月方源，候选被过滤成"**只有蛊牌**"（`GuCardRewardRules.CanAppear`，`GuCardRewardRules.cs:12-41`）。**已按裁决 D-12（方案 A）固化为设计口径**：角色卡池 = 蛊池，事件/修正器从角色池给牌一律给蛊（与战斗奖励同口径）；无色池/他角色池来源由 D-11 回退原版行为。两个附带结果均已接受：蛊池无 Power 型蛊，`InfestedAutomaton.Study`（专要 Power）自动走 D-11 回退给原版能力牌；`CharacterCards` 修正器并入的他角色牌被滤除、对古月方源无效化；
- **已按裁决 D-11（方案 A）修复**：原实现滤空时直接返回空集合，调用方用 `.First()` 会抛异常；且复核推翻了原文"该处用的是无色池，实际安全"的判断——`CanAppear` 对古月方源会把无色牌**全部滤光**，`EndlessConveyor.cs:181`（炸鳗鱼）、`AllStar.cs:28`、`Kaleidoscope.cs:45`（他角色池）恰是必崩点。现滤空时退出过滤作用域并放行原方法（等同未装模组的行为），放行期间 `TryModifyCardRewardOptions` 的剔除一并跳过；
- 初始转数抽取已由裁决 D-10 收敛：奖励走 `CardReward.Populate`，一切永久入组路径由 `GuDeckEntryRankPatch`（挂 `Hook.ShouldAddToDeck`）兜底补抽，变形结果由 `GuTransformRankPatch` 补赋（D-04），见 §6.7。

涉及位置：`InfestedAutomaton.cs:31,46`、`BrainLeech.cs:56-74`、`RoomFullOfCheese.cs:40-44`、`EndlessConveyor.cs:180-182`，
以及修正器/遗物：`Modifiers/Specialized.cs:25`、`SealedDeck.cs:31`、`Insanity.cs:31`、`AllStar.cs:28`、`CharacterCards.cs:54`、

### 6.7 转数缺口 ✅ 已按裁决 D-10（方案 C 式落地）修复

原缺口：`GuRankRewardPatch` 只挂在 `CardReward.Populate`（`GuRankRewardPatch.cs:33-44`）⇒ 一切不经 `CardReward` 的蛊牌来源（§6.6 的事件/遗物给牌、§6.4 的变形结果、§6.5 的克隆副本、任何直接 `CardPileCmd.Add(card, PileType.Deck)` 的路径）都不抽初始转数、不登记仙蛊。

落地（提交 `4678487`，三入口并存、随机流互相独立、全部复用 `AssignInitialRank` 原版正态分布）：
- 奖励：`CardReward.Populate` postfix（`reward/gu_rank` 流，界面预览即有转数，序列不变）；
- 永久入组兜底：`GuDeckEntryRankPatch` 挂 `Hook.ShouldAddToDeck`（`CardPileCmd.Add` 的 `PileType.Deck` 分支，全游戏唯一入组调用点；`deck_entry/gu_rank` 流；优先级晚于仙蛊仲裁，只给放行的牌赋阶）；
- 变形：`GuTransformRankPatch`（`transform/gu_rank` 流；变形走 `AddInternal` 不经 `ShouldAddToDeck`）。

幂等沿用旧版"已赋阶标记"机制（`NeedsInitialRankAssignment`），奖励流零消费不漂移；合练结果（材料最高+1）不会被覆盖；克隆副本继承母本转数（属 D-13，未裁决）。
